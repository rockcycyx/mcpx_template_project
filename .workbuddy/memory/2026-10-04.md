## 修复启动崩溃：Brush 属性误用 iNKORE Color 资源

### 问题
启动报 `InvalidOperationException: "#FF1C1C1C"不是属性"Background"的有效值`，栈定位 MainWindow.xaml:108（TreeView Background）。

### 根因
iNKORE 主题库里颜色资源**成对**定义：`SolidBackgroundFillColorSecondary` 是 **Color** 类型（深色主题值 `#FF1C1C1C`），`SolidBackgroundFillColorSecondaryBrush` 才是 **Brush** 类型。WPF 的 `Background`/`Foreground`/`BorderBrush` 要 Brush，我误把 Color 资源直接赋给 Brush 属性。浅色主题侥幸通过，深色主题（用户系统深色模式）下返回字符串 `#FF1C1C1C`，Brush 无对应 TypeConverter 导致崩溃。

### 修复
把所有「Brush 属性误用 Color 资源」改为 `*Brush` 后缀资源：
- MainWindow.xaml：3 处 Background（TreeView/底部状态栏/右侧工具栏）
- App.xaml：DataGrid 表头 Background + 表头/单元格 Foreground（TextFillColorPrimary→TextFillColorPrimaryBrush）
- PageUser/PageRole/PagePost/PageOperLog.xaml：各 1 处列表头 Background

### 验证
- 写 Python 脚本全项目 24 个 XAML 扫描，确认 Brush 属性（Background/Foreground/BorderBrush/Fill/Stroke）无任何 Color 资源误用。
- 编译通过（0 错误，6 个无害警告）。

### 经验教训（重要）
- **iNKORE 颜色资源命名约定**：无 `Brush` 后缀 = Color（用于 `SolidColorBrush.Color` 等 Color 属性）；`Brush` 后缀 = Brush（用于 Background/Foreground/BorderBrush/Fill/Stroke）。两者不能混用。
- 判断资源类型可用 Python 读 DLL 内字符串表确认 `*Brush` 资源是否存在（`TextFillColorPrimaryBrush`、`SolidBackgroundFillColorSecondaryBrush` 等均存在）。
- Bash 环境 PATH 彻底损坏（dirname/head/tail/find/rm 全 not found），构建必须用 PowerShell（`dotnet build ... | Select-Object -Last N`），文件增删改用 Python。

## 修复残留 CastException（HorizontalGridLinesBrush 漏网）

### 问题
上一轮修复后启动仍报 `System.InvalidCastException: Unable to cast object of type 'System.Windows.Media.Color' to type 'System.Windows.Media.Brush'`。

### 根因
上一轮扫描漏了 **App.xaml 第 52 行 DataGrid 全局样式**里的 `<Setter Property="HorizontalGridLinesBrush" Value="{DynamicResource DividerStrokeColorDefault}"/>`——`HorizontalGridLinesBrush` 是 Brush 属性，`DividerStrokeColorDefault` 是 Color 资源，导致 Color→Brush 强转失败。

### 确认 iNKORE 资源类型（决定性证据，从 GitHub 源码 Light.xaml）
- `<Color x:Key="SolidBackgroundFillColorSecondary">#EEEEEE</Color>` → Color 类型
- `<SolidColorBrush x:Key="SolidBackgroundFillColorSecondaryBrush" Color="{m:StaticColor ...}"/>` → Brush 类型
- 规律：无 `Brush` 后缀 = `<Color>`；`Brush` 后缀 = `<SolidColorBrush>`（内部用 `{m:StaticColor}` 引用 Color）。

### 修复
`HorizontalGridLinesBrush` → `{DynamicResource DividerStrokeColorDefaultBrush}`。全项目彻底扫描（不限属性名的 `{DynamicResource XXX}` 匹配）确认：除 App.xaml 里 15 处 `Color="{DynamicResource XXX}"`（Color 属性配 Color 资源，类型正确、安全）外，无其他 Brush 属性误用 Color 资源。

### 结果
编译通过（0 错误，6 个无害警告）。

## 修复 Status 被神秘改为 1 + FontIcon 官方用法迁移

### 问题 1：sys_user/sys_role(sys_dept) 的 Status 总是莫名变成 "1"（停用）
根因（两个叠加的坑，都在列表页 ToggleSwitch 上）：
1. **Toggled 事件在任何 IsOn 变化时都触发**（包括程序化赋值）。列表开关放在 DataGridTemplateColumn 里，DataGrid 默认行虚拟化——滚动/刷新时行容器重建，`IsOn` 绑定从新数据源重新赋值 → 触发 `Toggled` → 误执行 SwitchStatusCommand → 把 Status="0" 的行批量翻转成 "1"。Status="1" 的行（false→false 无变化）不再触发，于是数据单向漂移到 "1"，完全符合"不知道什么时机、总被改为 1"。
2. `IsOn="{Binding Status, Converter=...}"` 未写 Mode，若 IsOn 默认双向绑定，翻转时 ConvertBack 先写一次 Status，命令再翻转一次（双重写入）。

修复：
- `ToggleSwitchCommandBehavior` 重写：**不再订阅 Toggled**，改订阅 `PreviewMouseLeftButtonUp` + `KeyUp(Space)`（Preview 隧道事件先于控件处理，命令读到的是原始 VO 状态，方向一定正确）——只响应真实用户交互。
- PageUser/PageRole/PagePost 三处列表绑定显式 `Mode=OneWay`，命令成为唯一写入方。
- 部门页无状态开关（SwitchStatusCommand 未绑定，属死代码）；编辑/新增 VM 的 IsStatusActive→Status 映射（true→"0"）逐一核对无误。表里有 update_by/update_time 可事后追责。
- 经验：**DataGrid 里的事件型交互控件绝不能把"事件触发"当"用户点击"**，虚拟化重绑定会伪造事件。

## 修复 NavigationView 与内容区之间的"神秘间隔"

### 问题
NavigationView 窗格与右侧标签页区之间有一条固定空隙（展开时约 56px，收起后变成 232px 整条空白彻底显露），且空隙位置不随窗格展开/收起移动。

### 根因
MainWindow.xaml 的 DockPanel 里 `ui:NavigationView`（Dock=Left）与页面内容 Border（TabControl，DockPanel 填充）是**平级兄弟节点**，内容在 NavigationView 外部。而 iNKORE NavigationView 在 PaneDisplayMode=Left 下对外报告的期望宽度 ≠ 可见窗格宽度（约等于 OpenPaneLength+CompactPaneLength≈288），DockPanel 只能给到它的期望宽度，多出的部分就成了"谁也不是"的空隙；收起后窗格缩到 56px，空隙全额暴露。

### 修复（官方标准用法）
把 TabControl 的 Border 从 DockPanel 填充位**移入 NavigationView 的 Content**：

## 实测定案：登录窗亚克力两个真根因（运行时探针验证）

### 方法
Python+PIL+ctypes 探针：启动应用 → FindWindow/GetWindowRect → 截屏量化（stddev 判平坦）→ 查询 DWM 属性（DwmGetWindowAttribute）→ 运行时 SetWindowLong 注入样式做对照实验。此环境 PowerShell stdout 不可用、无 PIL（需 pip install pillow 到托管 venv）。

### 实测结论（决定性）
1. **DWM 背景只绘制在带 WS_THICKFRAME 的窗口上**。`ResizeMode="NoResize"` 移除 WS_THICKFRAME → `DWMWA_SYSTEMBACKDROP_TYPE=3` 虽已设置（iNKORE 确实生效）但 DWM 拒绝绘制 → 整窗纯色（背景完全平坦 sd=0.00）。运行时注入 WS_THICKFRAME 后背景立刻出现模糊纹理（sd>0）——实验直接证实。
2. **DWM 背景材质明暗变体由 `DWMWA_USE_IMMERSIVE_DARK_MODE`(attr=20) 决定，缺省浅色**。应用 WPF 主题跟随系统（深色），但 DWM 材质仍是浅色 → 深色系统下窗口发白，用户感知为"背景色跟随系统没生效"。设置 attr=20=1 后变深色磨砂。
3. **注入时机**：在 SourceInitialized 注入会被 WindowChrome 重算样式剥掉（实测 style 又变回无 THICKFRAME）；必须 **Loaded 之后（Dispatcher.BeginInvoke）** 注入才持久。
4. **主题判断坑**：`ResourceDictionary.Contains()` 不搜索 MergedDictionaries，判断应用明暗必须用 `Application.Current.TryFindResource("SolidBackgroundFillColorBase")`（Dark=#202020，Light=#F3F3F3）。
5. probe 期间登录窗背景色在深浅间变化 = 用户在切换系统主题测试（应用 WPF 主题确实跟随系统）。

### 修复（Helpers/DwmWindowHelper.cs 新建）
- `ApplyWindowBackdrop(Window)`：Loaded+BeginInvoke 后 (a) 补回 WS_THICKFRAME（对 NoResize 窗口仅用于 DWM；WindowChrome ResizeBorderThickness=0 仍拦截缩放，窗口实际不可缩放）；(b) 按解析主题设 DWMWA_USE_IMMERSIVE_DARK_MODE。
- Login.xaml.cs：`OnSourceInitialized` 调用；MainWindow.xaml.cs：SourceInitialized 钩子里调用（主窗口本有 THICKFRAME，只为拿深色材质）。
- 实测复核：THICKFRAME=True、IMMERSIVE_DARK_MODE=1、NCRENDERING_ENABLED=1、背景 mean≈111 有纹理——深色磨砂生效。

### 局限
immersive dark 只在启动时设置；运行中切系统主题不会实时跟随（iNKORE 画刷会变，DWM 材质不变）。需要实时跟随可再加 UserPreferenceChanged 监听。

### 结果
编译通过（0 错误，0 警告），探针截图确认深色亚克力 + 模糊纹理 + 圆角。

## 修复登录窗口启动异常（AllowsTransparency 与 Acrylic 冲突）

### 现象

### 根因

## 关键发现：iNKORE 无 DataGrid 样式，选中色需覆盖系统高亮色

### 结论（决定性）
- **iNKORE.UI.WPF.Modern 完全不提供 DataGrid 样式**：扫描 3 个 DLL（Modern.dll / Modern.Controls.dll / UI.WPF.dll）的 UTF-16 字符串，`DataGrid`/`DataGridRow`/`DataGridColumnHeader`/`DataGridCell`/`DataGridTemplateColumn` 全部 0 次。表格一直是 **WPF 原生 System.Windows.Controls.DataGrid**（老式默认外观），不是自绘、也没套 Fluent 样式。
- **为什么改 Style 的 Background 改变不了选中色**：WPF 原生 DataGridRow/DataGridCell 模板里，`IsSelected` 触发器用 `Setter TargetName="DGR_Border" ...` 直接设 Border.Background = `{DynamicResource SystemColors.HighlightBrushKey}`（系统蓝）。TargetName 触发器 = 本地值，优先级高于样式 Setter/触发器，所以任何属性级 Background 设置都被它盖住。

### 修复（最小且零模板风险）
在 App.xaml 重定义系统高亮色，指向 Fluent 主题色（DynamicResource 嵌套实现明暗跟随）：
```xml
<SolidColorBrush x:Key="{x:Static sys:SystemColors.HighlightBrushKey}" Color="{DynamicResource AccentFillColorSecondary}" />
<SolidColorBrush x:Key="{x:Static sys:SystemColors.HighlightTextBrushKey}" Color="{DynamicResource TextFillColorPrimary}" />
```
需加 `xmlns:sys="clr-namespace:System.Windows;assembly=PresentationFramework"`。选中色立即从系统蓝→主题浅底 AccentSubtle，文字 primary，深色主题自动跟随。副作用极小（本应用已全面 Fluent 化，仅登录页 Style={x:Null} 的原生 TextBox 文字选中会变浅蓝，反而更协调）。

### 经验教训
- **WPF 原生控件（DataGrid/ListBox/ComboBox 等）的选中高亮默认走 SystemColors.HighlightBrushKey，且用模板 TargetName 触发器绘制**，优先级高于任何样式 Setter。要改选中色，最稳的办法是重定义 `SystemColors.HighlightBrushKey`/`HighlightTextBrushKey`，而不是改模板或设 Background。
- 判断一个控件是否被 UI 库套了样式：扫描该库 DLL 的字符串表看有没有对应的 `TargetType` 资源名。

## DataGrid Fluent 完整重渲染（解决白表头/上下不齐）

## 关键坑：DataGridColumnHeader 隐式样式不可靠 → 必须显式挂 ColumnHeaderStyle

## 重大教训：空字符串 new_string 的 Edit 删除实际不生效 + 内联 HeaderStyle 优先级

### 现象
用户反复反馈"表头没变化/有的列生效有的列没生效"。最终 Grep 发现：4 个页面的 23 处文本列 + 6 处模板列的内联 `<DataGridTextColumn.HeaderStyle>`（只设 HorizontalContentAlignment、无 BasedOn）**全都在**——之前用 `new_string=""`（空字符串）+ replace_all 删它们的操作，**工具返回"成功"但磁盘内容根本没变**。

### 根因（两层）
1. **空字符串 new_string 的 Edit 会"假成功"**：删除文本时 new_string 不能是空串（会静默无效）。要用非空替换（如改成 `BasedOn=...` 单行版）才真正落盘。
2. **列级 `HeaderStyle` 优先级 > `DataGrid.ColumnHeaderStyle`**：这些内联 HeaderStyle 无 BasedOn → 整列表头回退 WPF 原生白底模板，盖掉全局/ColumnHeaderStyle。OperLog 里唯一没 HeaderStyle 的"系统模块"列显示深色，正好解释了"有的列生效有的列没生效"。

### 修复
4 个页面所有内联 HeaderStyle 统一改为显式继承：
```xml
<Style TargetType="DataGridColumnHeader" BasedOn="{StaticResource FluentDataGridColumnHeader}"/>
```
OperLog 的旧版 ElementStyle 同步改为 `BasedOn="{StaticResource DataGridCenterText}"`。

### 经验教训（必记）
- **删除/清空一段文本，绝不用 `new_string=""`**——会假成功。改为替换成有意义的内容，或连同前后行一起用非空 new_string 覆盖。
- 改完后必须 **Grep 复核目标字符串是否真的消失/出现**，不能只信 Edit 的"成功"返回。这次就是靠 Grep `HorizontalContentAlignment` 才发现 HeaderStyle 根本没删掉。

### 结果
编译通过（0 错误，6 个既有无害警告），exe 成功复制（程序已关闭）。

## Copilot sprite 长图动画头像（个人中心）

### 需求
把 Assets/images/Copilot.svg（GitHub Copilot idle 动画的 sprite 长图）做成个人中心页的动态头像，等价于 GitHub 网页上 `--copilot-animation-sprite` + CSS background-position 的效果。

### SVG 结构确认
`viewBox="0 0 32 1728"` = **垂直 sprite：54 帧、每帧 32×32 上下排列**（1728/32=54），单色 fill=#000。

### 实现步骤
1. **SVG→PNG**：node managed 环境（22.22.2）+ sharp（`npm install sharp --prefix <workspace>`）。density=288（72*4）放大 4x，输出 `Assets/images/Copilot_sprite.png` = **128×6912**（每帧 128）。转换脚本放 workspace（convert_copilot.js），结果写日志文件再 Read 确认。
2. **csproj**：加 `<Resource Include="Assets\images\Copilot_sprite.png" />`。
3. **XAML（PageUserCenter）**：头像区 = 底层 Accent 淡色圆 + `Rectangle`(80×80)，`Fill` 用主题色 `TextFillColorPrimary`，`OpacityMask` = `ImageBrush`(sprite, Stretch=Uniform, Viewbox="0,0,128,128" ViewboxUnits=Absolute, Viewport="0,0,80,80")。**OpacityMask 用 sprite 的 alpha 通道 → 图标颜色完全跟随主题（深浅色自动适配）**。
4. **动画（xaml.cs）**：`DispatcherTimer`(40ms≈25fps) 逐帧更新 `SpriteMask.Viewbox = new Rect(0, frame*128, 128, 128)`，循环 54 帧（≈2.2s/轮，与 GitHub idle 节奏一致）；`Unloaded` 停 timer 防泄漏。

### 坑
- **PowerShell 直接跑 node 脚本 stdout 经常不被捕获**（exit 0 但看不到输出）——node 脚本里把结果写日志文件再 Read，别依赖 stdout。
- npm 的 notice 走 stderr，PowerShell 会当 NativeCommandError 报 exit 1，但 `added 8 packages` 说明实际安装成功，别被吓到。

### 结果
编译通过（0 错误，6 个既有无害警告）。运行个人中心页即可看到 Copilot 头像循环动画。

### 修正：ImageBrush Viewbox 取帧错乱 → 改 Image+Clip+Translate
- **现象**：ImageBrush(OpacityMask) + Viewbox/Viewport + Stretch=Uniform 组合下，头像一次露出 3 帧（取帧区域不可控），且 40ms/帧偏快。
- **修复**：放弃 ImageBrush 取帧，改为**整图 Image（宽 80、高 4320 = 6912 等比缩放）+ 外层 80×80 Grid(ClipToBounds=True) + TranslateTransform 位移**，逐帧上移 `SpriteTranslate.Y = -frame * 80`。这正是 CSS `background-position` 的等价实现，行为完全可预期。
- **节奏**：40ms→60ms/帧（54 帧约 3.2s/轮）。
- 经验：**WPF sprite 动画优先用 Image + 裁剪窗口 + TranslateTransform**，别用 ImageBrush 的 Viewbox/Viewport（单位/Stretch/TileMode 组合坑多，尤其做 OpacityMask 时取帧会漂）。

### 再修正：ClipToBounds 不裁剪 RenderTransform → 改 Canvas.Top 布局定位
- **现象**：Image + Grid(ClipToBounds) + TranslateTransform 方案下，动画只有第一帧、之后全空白。
- **根因**：`ClipToBounds` 裁剪的是子元素**布局边界**，而 `RenderTransform` 在布局之后应用、不参与裁剪 → 第一帧被裁掉后移出窗口，后续帧在布局坐标里本就被裁掉了，全空白。
- **修复**：把位移动画作用在 **`Canvas.Top`（布局定位，非 RenderTransform）** 上：`Canvas.SetTop(AvatarImage, -frame * 80)`，外层 `Canvas`(80×80, ClipToBounds=True)。布局定位参与裁剪，逐帧正确显示。
- **最终结论（sprite 动画正确姿势）**：`Canvas`(固定尺寸 + ClipToBounds) 内放整图 `Image`(Canvas.Top/Left 定位)，动画改 `Canvas.SetTop/SetLeft`。**不要用 RenderTransform，也不要用手动 TranslateTransform 配合 ClipToBounds**。

## 弹窗服务改为 FluentUI ContentDialog

### 背景
项目弹窗统一走 `IDialogService`（`Service/Admin/impl/DialogService.cs`），内部用**老式 WPF MessageBox**。用户要求改成 FluentUI 弹窗。

Dispatcher.PushFrame(frame);

- 结论：**FontIcon 图标一律用 `SegoeFluentIcons.XXX` 属性，不要用 `CreateIcon(int)`**（后者只在 MenuIconConverter 里用于运行时把 4 位 hex 码动态转图标，且那里最终也是配合 XAML 字体族才 OK）。

- 根因：个人中心页 TabControl 用 iNKORE 默认 TabItem 样式（含 `TabStripPlacement` 的 FindAncestor TabControl 触发器），切页卸载 TabItem 时绑定找不到源 → 报 `System.Windows.Data Error: 4`。
- 修复：给 PageUserCenter 的 TabControl 加 `<TabControl.Resources>` 里**自定义 TabItem 样式**（重写 ControlTemplate，去掉 TabStripPlacement 绑定），参考 MainWindow.xaml 的标签页 TabItem 样式（ContentBorder 圆角 + Accent Underline 指示条 + 悬停/选中触发器）。
- 结论：要用 TabControl 且不想看到 TabStripPlacement 报错，就**别用 iNKORE 默认 TabItem 样式**，自己写一个（或 BasedOn 后重写模板去掉该绑定）。

## 三连修复：菜单 parent_id / SegoeFluentIcons 反射 / 断点符号
1. **新增菜单目录 parent_id=0**：`AddEditMenuViewModel.ToEntity()` 里 `ParentId = MenuType == "M" ? 0 : (ParentId ?? 0)`。原来未选上级存 NULL，菜单树构建（HasValue 判断）会把它当孤儿丢掉。
2. **SegoeFluentIcons 反射拿不到图标**：图标成员是**静态只读字段**（field）而非属性，`GetProperties` 只拿到被跳过的 FontFamily → cache 空（`_officialIcons` Count=0 且 `if(_officialIcons==null)` 永不进）。修复：`GetProperties` + `GetFields` 双遍历。
3. **TryGetValue 断点"未加载符号"**：Dictionary.TryGetValue 在 .NET 运行时库（System.Private.CoreLib），项目没加载 .NET 库 PDB 符号 → 断点不命中。不是 bug；VS 里 工具→选项→调试→符号 勾"Microsoft 符号服务器"即可单步进库代码，否则只在业务代码断点。
